# Beauty Salon OS V14 — 等候名单与取消补位 + V13 审计修复

日期：2026-11-19（日本时间）
基线：V13 候选源码（中日平台安全接入与预约核对）＋ V12 线上部署版的修复回归处理。

## 一、本轮新功能：等候名单与取消补位（V14）

门店每天的真实痛点：热门时段满约后顾客直接流失；有人取消时，店长靠记忆翻聊天记录找人补位。

- **数据**：迁移 `0009_waitlist` 新增 `waitlist_entries`（门店隔离、希望日期＋时间窗、状态机 waiting→notified→booked/expired/cancelled）。等候条目**不是预约、不占任何工位/技师时段**，从设计上不可能造成双重占用。
- **顾客端**：所选日期无空位时，预约页直接出现等候登记卡（姓名/手机号与预约表单共用、希望时段默认取当天营业时间）。同门店＋同手机号＋同日＋同项目的重复登记**幂等返回原条目**，不堆重复数据；手机号已是本店顾客时自动关联客户档案。
- **店长端**：新增「等候名单」页——按日查看登记（先到先得排序）、标记已通知/已成约/过期/取消（全部写审计日志）；「补位候选查询」输入空出的时间，立即列出时间窗覆盖该时刻的等候顾客。
- **权限**：等候名单仅店主/店长可见（技师 403）；跨门店不可见。公开加入接口有独立限流（10 次/分钟/IP）。
- **测试**：新增 `apps/api/src/waitlist.test.ts` 6 个真实 PostgreSQL 场景（幂等、校验、自动关联顾客、权限与门店隔离、候选匹配、状态流转与审计）。

## 二、V13 审计修复（部署前拦截的问题）

上游 V13 候选包在其环境未跑类型检查与 PG 测试，本轮逐项验证后修复：

1. **迁移日志缺失 0008**：`meta/_journal.json` 没有登记 `0008_integration_inbox`，Drizzle 迁移器会静默跳过该迁移——平台接入功能在任何环境部署后都会因表不存在而 500。本轮补登记（V14 另加 0009），并做了 V12→V14 迁移预演（日志 8→10 条、数据完好）。
2. **V12 三处修复在 V13 中回归**，已重新应用：员工仅改技能时 PUT 500（Drizzle 空 set）；门店设置 bookingWindowDays 上限 365 与系统种子 3650 冲突导致回显保存 400；V8 测试时间 11:40 与种子 15 分钟缓冲自相矛盾（应用是对的，测试改 11:45 并留注释）。
3. **类型错误 2 处**：`integration-contract.ts` 在 noUncheckedIndexedAccess 下 `match[2]` 可能为 undefined；`api.test.ts` bridge 助手 body 类型为 unknown。
4. **等候名单子应用中间件范围过大**：子应用挂载在 `/admin` 且用 `use("*")` 做店长鉴权时，会拦截其他 `/admin/*` 路由的技师请求（全量测试中一条既有权限用例回归 403）。已把中间件收窄到 `/waitlist` 路径，并由全量测试验证。
