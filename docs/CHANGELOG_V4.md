# Beauty Salon OS V4 — 实际源码修复记录

基于用户上传的 `Beauty_Salon_OS_V3_继续修复源码.zip` 做增量修改。没有覆盖现有业务数据库，也没有连接用户服务器。

## 1. 身份认证与权限

- 新增 `auth_sessions` 数据表及 **0003_auth_sessions.sql** 迁移，JWT 只携带用户 ID 和随机 session ID，不再在 JWT 内固化员工权限。
- 每次后台 API 请求查询数据库中的会话（必须未撤销、未过期）及当前用户（必须有效）；角色、门店和关联技师均以当前数据库状态为准。
- 退出登录会撤销服务端的对应会话，复制旧 Cookie/JWT 也不可再使用。
- 店主修改账号密码、权限、启用状态或技师绑定时撤销该账号之前的会话。
- 禁止店主自己停用自己的账号或降低自身角色，避免常见的意外锁号。
- V3 旧 JWT 不再兼容，升级后后台账号必须重新登录；不会删除客户或预约记录。

## 2. 预约一致性

- 顾客自行改期使用与新建预约相同的提前预约限制与开放窗口限制，且在事务内二次校验。
- 取消时在数据库事务中重新校验状态：到店、服务中、完成等状态不再可从顾客端取消。
- `/public/availability` 不再返回过去的日期或门店可约窗口以外的时段。
- 服务组合最多 8 项、附加项目最多 24 项（单项目最多 8 项），重复或已停用的附加项目会被拒绝。
- 公开预约查询不再返回内部 `serviceNote`（此前仅隐藏 `internalNote`）。
- 通知唤醒失败不再让已经落库成功的预约返回 500；任务仍写在 `notification_jobs`，由 Worker 从数据库补发。
- 店长端预约状态变更在同一门店事务锁下重新读取当前状态，避免多人同时操作发生过期状态写入。

## 3. 多门店隔离和财务

- 禁止将其他门店的技师用于排班批量生成、请假，以及创建或编辑员工登录账号。
- 禁止将其他门店的资源用于本店封锁日程。
- 手工收款关联客户时检查客户是否属于当前门店。
- 退款改为 PostgreSQL 事务＋原收款行锁，校验累计退款、写入负数退款记录、更新原单状态一并提交；并发退款不能超过原始付款金额。**仅限系统内台账**，不代表已向银行卡/支付平台发起真正资金退回。

## 4. 新增测试

- 扩展集成测试：注销后旧令牌失效、员工停用及重新启用后的会话吊销、权限变更后的强制重新登录、跨店员工绑定、公开改期提前预约、并发退款。
- 现有 V2/V3 排单、并发占用、护理档案、Cookie、CSRF 等回归测试保留。

## 5. 本轮实际验证

- **通过：** 77 个 TS/TSX 文件语法解析、152 个本地相对导入路径解析、4 个迁移条目及其 SQL/快照文件存在性检查。
- **通过：** 不依赖外部 npm 包的独立运行冒烟检查：组合项目时长与价格、资源可约／冲突、在线预约提前时间和日期窗口。
