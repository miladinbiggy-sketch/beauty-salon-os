# Beauty Salon OS V12 — 收银和退款安全重试、原子审计

日期：2026-11-19（日本时间）。代码真实基线为 `Beauty_Salon_OS_V11_营业时间与预约菜单保护候选源码.zip`，SHA-256 `578a043efa029714364962eb14f41158fdc4a305792e149e8deb91c24e81b2ad`，本轮已重新核验，与原记录一致；V7–V10 候选亦已重新校验且 ZIP CRC 正常。**旧版本未丢弃、未覆盖。**

## 真实问题与复现

- 收银员登记 ¥7,200 的支付，POST 写库成功但手机网络断开。原有前端重新点击会再次插入一条 ¥7,200，导致重复收款流水、顾客余额错记或日结金额偏大；退款重复提交可能把同一原支付过度扣除。
- `writeAudit` 原独立于支付事务而且吞掉错误，导致付款成功但审计缺失。与钱相关的行为必须要么同时写入审计、要么整体回滚。
- 在业务日结锁账后，原本成功而未收到回执的请求应当返回原记录，**不能**因为今天已经锁账就无法恢复；同时新请求仍必须拒绝。

## 实际改动

1. `packages/database/migrations/0007_payment_idempotency.sql`、`schema.ts`：为每笔支付/退款提供可空的请求 UUID、64 位 SHA-256 指纹和按 `(store_id, idempotency_key)` 唯一约束。旧流水保持 null，无需回填；成对 CHECK 避免脏数据，迁移增量不覆盖旧记录。前置迁移 `0000–0006` 必须保留。
2. `apps/api/src/services/payment-idempotency.ts`：明确区分收款和退款操作、原付款 ID、金额、方式、外部交易号、记录时间和备注；只存 SHA-256 摘要、不把内容原文写到去重字段。日期输入规范化为 UTC ISO。
3. `apps/api/src/routes/admin.ts`：收款/退款在已有门店日结 advisory 事务锁内先检查请求键，保持同键同内容返回旧流水 HTTP 200、新操作返回 201、同键不同内容返回 HTTP 409；**回放检查先于锁账检查**。原支付剩余额、门店归属、日结检查与 INSERT 同事务。新建交易及审计一起插入并提交，若审计出错则交易回滚。`GET /admin/payments` 与 POST 响应都不下发内部去重指纹或键。
4. `apps/admin-web/src/lib/api.ts`、`lib/payment-retry.ts`、`pages/Payments.tsx`：前台有明确的 `Idempotency-Key` 支持，每次新交易采用 `crypto.randomUUID()`；请求超时后，原表单不变就沿用同一键再次点击；修改金额或退款目标会生成新键；收到成功回执后清除。不中途保存到 localStorage，也不会把顾客内容外发给模型。中日文提示提醒不要改动内容再试。
5. 新增 `tests/payment-idempotency-unit.test.mjs`、`tests/payment-retry-ui-unit.test.mjs`，以及 `apps/api/src/api.test.ts` 中 3 组 PostgreSQL 真实并发设计场景：同 UUID 并发付款、结账后按原 UUID 恢复、同 UUID 并发退款与跨操作冲突，并核验审计条数。

## 语义与边界

- **只保证本系统数据库交易在有效 UUID 前提下的重复请求去重，不代表银行卡、PayPay、LINE 等外部资金清算一定成功/去重。** 支付服务商必须独立调用官方 API 幂等机制并做对账；本系统的退款记录目前不是对外部支付商发起退款指令。
- 旧 API 客户端如果不传请求头 `Idempotency-Key`，依旧允许写入以兼容老客户端，但**不能**防止同一业务请求重复入账。计划生产开放前可在升级旧客户端后强制此头。
- 当前 UI 保存 UUID 于内存，原页面内重试安全，刷新/关闭网页后不能恢复原 UUID；不能宣传完整断电恢复。这种情况下应先查询交易记录，再重新发起操作。
- UUID 必须是随机、足够不可预测的 v4；同一商户同一 UUID 不能用于另一笔支付/退款，金额或原退款目标变更会返回 409。
- 同一门店收款和退款的读改写通过 `cashLedgerLock` 序列化；数据库唯一索引是最终防线。直接 SQL 操作和无键旧客户端不具备同样保障。
- audit insert 是事务的一部分，涉及资金时不再容忍静默审计失败；这会降低异常情况下的可用性，但是安全、可追溯优先。

## 数据库上线 / 回退注意

1. 升级前备份、在**完全不含真实顾客的测试环境**恢复演练并停止旧版 API/Worker。按序执行 `0000–0007` 迁移，确认 `payments_store_idempotency_key_unique` 存在后再启动 V12 API 和前台。
2. 升级后用测试商户验证：两次相同 UUID 均返回同一 `payment.id`、一个日结快照不会变化、改金额复用 UUID 为 409、两次并发退款只记一笔、审计数为一。验证支付平台实际扣款与本地流水一致。
3. 不能简单把应用回滚到 V11 并继续收款：旧应用不发送 UUID，后续仍会重复记账；跨版本回退必须先停写、保留新字段和历史流水，再由人工审核对账。数据库迁移无法安全直接倒回（会丢掉去重事实），不提供盲目 DROP 回退脚本。
